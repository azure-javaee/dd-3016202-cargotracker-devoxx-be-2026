The intended use of `shepherd-task-15-prepare-create-issues.sh` is as a non-interactive adapter and launcher generator between the resolved campaign plan and agent-driven Stage 20. It does not itself create GitHub issues.

The normal lifecycle is:

1. Stage 00 initializes the campaign, producing the campaign directory, manifest, campaign issue, base branch, and lesson mode.
2. Stage 10 creates the ignorance-reduction plan.
3. Humans and Copilot complete the research gate and fill every implementation-gating `Resolution` block.
4. Commit and push the resolved plan and campaign metadata to the campaign base branch. This matters because Stage 15 examines the local file, while Stage 20 rereads the plan from `BASE_BRANCH`. The fixture commits and pushes everything in `01-prepare-base-branch.sh`.
5. From the campaign worktree root, run:
"$HOME/.copilot/plugins/shepherd-task/scripts/shepherd-task-15-prepare-create-issues.sh" \
  <campaign-directory-basename>
6. Execute the invocation script generated by Stage 15. That launcher invokes the `shepherd-task-20-create-issues-from-plan` skill in a new Copilot CLI session.
7. After successful Stage 20 completion, take the ordered issue numbers from the creation ledger/handoff and pass them to Stage 25.

Stage 15 exists to derive error-prone Stage 20 inputs rather than requiring the user to supply them manually. It validates and derives:

- campaign identity, repository, base branch, parent issue, and lesson mode from `shepherd-campaign.json`;
- the one ignorance-reduction plan in the campaign directory;
- the unique `## …Ignorance reduction…` heading;
- the unique task-bearing `## …Implementation…` heading;
- the number of direct `###` task subsections;
- the Git remote matching the manifest repository;
- absolute paths to the Stage 20 validators and verifiers.

It then creates a timestamped directory such as:

<campaign-directory>/prompts/shepherd-task-20-YYYYMMDD-HHMM/

containing:

YYYYMMDD-HHMM-invoke-shepherd-task-20-create-issues-from-plan-skill.md
YYYYMMDD-HHMM-invoke-shepherd-task-20-create-issues-from-plan-skill.sh

The Markdown file is the fully populated Stage 20 prompt. The executable script:

- feeds that prompt to `copilot --yolo`;
- captures the shared session, JSONL output, and OpenTelemetry output;
- redacts secrets;
- requires `stage-20-result.json` to report successful completion;
- checks that the Stage 20 result has the expected number of created tasks.

The Cargo Tracker fixture demonstrates this contract through `02-create-issues.sh`:

1. Snapshot existing Stage 20 artifact directories.
2. Run Stage 15.
3. Require exactly one new artifact directory.
4. Require exactly one generated prompt and one launcher.
5. Verify that Stage 15 derived the expected plan filename, headings, task count, remote, and helper-script paths.
6. Append a fixture-specific pagination instruction to the generated prompt.
7. Execute the generated launcher.
8. Validate `stage-20-result.json` and `creation-ledger.json`.
9. Reverify every persisted issue body and child link.
10. Write an ordered handoff consumed by Stage 25.

The pagination text appended by the fixture is test instrumentation, not part of normal Stage 15 usage.

So the key operational distinction is:

Run Stage 15
    ↓
inspect/use its generated prompt and launcher
    ↓
run the generated launcher
    ↓
Stage 20 creates and verifies the ordered issues
    ↓
run Stage 25 with those issue numbers

It is therefore inaccurate to think of Stage 15 as “the script that creates issues.” It prepares and launches the separately auditable Stage 20 Copilot session. Also, because Stage 20 is deliberately one-shot, a partial issue-creation failure requires deleting every issue recorded in its ledger before generating/running another Stage 20 attempt.

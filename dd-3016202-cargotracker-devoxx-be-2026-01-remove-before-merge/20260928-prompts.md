### Copilot

You are right: the abstract’s order is a **rhetorical order**, not an optimal implementation order. A more useful categorization uses two independent dimensions:

1. **Enforcement surface:** where the safeguard operates.
2. **Engineering concern:** what kind of failure it prevents.

Trying to force each reason into one category such as “security” or “source code” loses important relationships.

## Categorization by enforcement surface

### A. Language and programming-model constraints

These influence what agents can express in production source code.

1. **Type system**  
   The compiler constrains API calls, values, generics, domain boundaries, and method contracts.

7. **Virtual threads and structured concurrency**  
   These affect application design and source code directly, but require Java 21 or later. Cargo Tracker currently uses `maven.compiler.release` 17, so this should be treated as a separate experiment rather than an early baseline modification.

These are not primarily CI features. CI makes their effects visible and enforceable.

### B. Build, compatibility, and dependency governance

These define the environment in which source code is allowed to build.

3. **Backwards compatibility culture**  
   Enforces Java 17, Java EE 7, `javax.*`, existing contracts, runtime compatibility, and preservation of historical behavior.

5. **Build system maturity and dependency management**  
   Governs Maven plugins, dependency versions, convergence, approved repositories, reproducibility, vulnerabilities, and packaging.

These should be established early because nearly every later check depends on a stable build model.

### C. Source inspection and repository consistency

These consume source code without ordinarily running the application.

4. **Deep static analysis**  
   SpotBugs, PMD, dependency analysis, architectural rules, and security-oriented source analysis.

6. **Code formatting and style enforcement**  
   Spotless, Checkstyle, license rules, and deterministic source layout.

These provide fast, deterministic feedback and should run before expensive integration or runtime jobs.

### D. Executable behavioral verification

2. **Testing ecosystem**  
   Unit, integration, architecture, regression, and acceptance tests execute code to verify behavior.

Testing deserves its own category. It is neither merely source inspection nor operational monitoring. It verifies externally meaningful contracts and catches defects that compile-time and static checks cannot.

### E. Runtime operability and empirical feedback

8. **Observability stack**  
   Logs, metrics, traces, exception reporting, correlation, and diagnostic artifacts explain what the running system did.

9. **JVM performance tuning**  
   Heap behavior, garbage collection, startup, warmup, memory limits, CPU limits, JFR, and `jaz` concern how the running JVM behaves under constraints.

Performance work should generally follow observability because meaningful tuning requires reliable measurements.

## Cross-cutting engineering concerns

The same nine reasons can also be viewed through a separation-of-concerns lens:

| Concern | Contributing reasons |
|---|---|
| **Correctness** | 1 Type system, 2 Testing, 4 Static analysis |
| **Maintainability** | 1 Type system, 4 Static analysis, 6 Formatting/style |
| **Compatibility** | 3 Backwards compatibility, 5 Build/dependency management |
| **Supply-chain security** | 4 Static analysis, 5 Dependency management |
| **Application security** | 1 Type system, 2 Testing, 4 Static analysis, 8 Observability |
| **Concurrency and scalability** | 7 Virtual threads/structured concurrency, 9 JVM tuning |
| **Operability** | 8 Observability, 9 JVM tuning |
| **Reproducibility** | 2 Testing, 3 Compatibility, 5 Build system, 6 Formatting |

**Security should therefore be a cross-cutting lane, not a bucket containing one abstract reason.** For example:

- dependency vulnerability detection belongs under reason 5;
- insecure-code analysis belongs under reason 4;
- security behavior tests belong under reason 2;
- secret and sensitive-data handling in telemetry belongs under reason 8.

## Recommended implementation order

The implementation order should follow dependencies and preserve green CI—not the order in the abstract.

### 0. Establish the trustworthy CI baseline

This is a prerequisite rather than one of the ten reasons:

- make `...-experiment` receive an authoritative workflow run;
- preserve the existing green `formatting` and `build` jobs;
- record commands, runtime versions, and expected artifacts;
- require green status after every increment.

### 1. Stabilize the build and dependency foundation

5. **Build system maturity and dependency management**

Establish Maven Enforcer rules, dependency convergence, plugin/version controls, repository policy, and reproducible packaging first. Every subsequent tool will be installed and run through this foundation.

### 2. Encode compatibility boundaries

3. **Backwards compatibility culture**

Make the intended baseline executable:

- Java 17;
- Java EE 7 and `javax.*`;
- Open Liberty 26.0.0.8;
- WAR packaging;
- preservation of existing APIs and runtime behavior;
- rejection of accidental Jakarta, framework, or runtime migration.

This prevents later agents and tools from “modernizing” away the experiment.

### 3. Preserve the existing fast formatting gate

6. **Code formatting and style enforcement**

Spotless is already present and green. Keep it as an early CI gate, then add only narrowly justified style checks. This is largely an existing capability to preserve rather than a new system to design.

### 4. Make compiler and type-system evidence explicit

1. **Type system**

Compilation already occurs, but the demonstration can strengthen and expose it through compiler warnings, API-boundary checks, and deliberately captured examples of invalid agent changes. Avoid adding tools merely to claim that Java has a type system.

### 5. Build the behavioral safety net

2. **Testing ecosystem**

Add tests in increasing cost order:

1. focused unit tests;
2. domain and application-service tests;
3. architecture tests;
4. Open Liberty integration tests;
5. HTTP or UI acceptance tests.

This is likely the most important protection before Shepherd Task starts changing the application.

### 6. Add deep static analysis

4. **Deep static analysis**

Introduce analyzers one at a time, establish a clean baseline, and make each check required before adding the next. Static analysis often exposes substantial legacy debt, so adding several analyzers simultaneously would conflict with the continuous-green invariant.

### 7. Instrument runtime behavior

8. **Observability stack**

Once the application has stable builds and behavioral tests, add structured logs, metrics, traces, correlation, and persisted diagnostic artifacts. Observability should explain both test failures and later campaign behavior.

### 8. Add measured performance experiments

9. **JVM performance tuning**

Only after stable workloads and telemetry exist should CI introduce:

- constrained container execution;
- startup and warmup measurements;
- heap and GC evidence;
- JFR artifacts;
- `java` versus `jaz` comparisons;
- narrowly defined regression thresholds.

Otherwise, performance measurements risk becoming noisy numbers without explanatory context.

### 9. Treat concurrency modernization as a separate spike

7. **Virtual threads and structured concurrency**

This should come last or remain outside the primary campaign because it conflicts with the Java 17 baseline. Options include:

- a separate Java 21 CI experiment;
- an isolated benchmark or companion module;
- a documented negative result: the compatibility constraint correctly prevents using the feature;
- postponing it rather than distorting Cargo Tracker merely to cover all ten reasons.

## Resulting order

The likely implementation sequence is therefore:

1. CI baseline and experiment-branch triggering
2. **5 — Build and dependency management**
3. **3 — Backwards compatibility**
4. **6 — Formatting and style**
5. **1 — Type system**
6. **2 — Testing ecosystem**
7. **4 — Deep static analysis**
8. **8 — Observability**
9. **9 — JVM performance tuning**
10. **7 — Virtual threads and structured concurrency**, as an isolated spike or explicitly unsupported reason

This produces four meaningful implementation phases:

- **Foundation:** 5, 3
- **Fast deterministic gates:** 6, 1, 4
- **Behavioral verification:** 2
- **Runtime evidence:** 8, 9
- **Compatibility-breaking capability spike:** 7

I would move testing ahead of deep static analysis in actual implementation, despite grouping static analysis with the fast gates, because protecting Cargo Tracker’s behavior is more important than maximizing analyzer coverage before the agentic campaign begins.
